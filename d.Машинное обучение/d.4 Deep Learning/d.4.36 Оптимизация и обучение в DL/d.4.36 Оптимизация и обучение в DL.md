## 1. Инициализация весов *(спрашивают на собесах)*

Перед первым шагом обучения весам нужно дать **какие-то** начальные значения. Кажется, что неважно какие — всё равно потом подстроятся. Это не так.

### 1.1. Почему нельзя все веса = 0 (или одной константе)

Возьмём скрытый слой из **двух** нейронов. Вход x = (1, 2). Все веса поставили одинаковыми, например 0.5 (с нулём то же самое).

| | вес при x₁ | вес при x₂ | выход z |
| --- | --- | --- | --- |
| нейрон 1 | 0.5 | 0.5 | 0.5·1 + 0.5·2 = **1.5** |
| нейрон 2 | 0.5 | 0.5 | 0.5·1 + 0.5·2 = **1.5** |

Оба нейрона выдали одно и то же. Дальше:

1. На backward оба получают **одинаковый** градиент (они стоят в одинаковом положении).
2. После шага оба веса станут, например, 0.4 и 0.4 — снова одинаковые.
3. И так навсегда: нейроны-**близнецы**. Сколько их ни ставь в слой — работает как один.

> Аналогия: нанял 100 сотрудников, но всем дал одну и ту же инструкцию и одни и те же исправления. Получил одного сотрудника в 100 копиях.

Поэтому веса стартуют **случайными** — чтобы нейроны с самого начала были разными («сломать симметрию»).

### 1.2. Какие случайные числа

Слишком большие случайные веса → сигналы по слоям раздуваются; слишком маленькие → затухают до нуля. Нормальные схемы подбирают разброс так, чтобы масштаб сигнала и градиентов сохранялся от слоя к слою.

| Имя | Когда вспоминать |
| --- | --- |
| Xavier / Glorot | под tanh / sigmoid |
| **Kaiming / He** | под **ReLU** (твой обычный случай) |

**На практике:** в PyTorch у `nn.Linear` уже адекватный дефолт. Главное — **не обнулять веса руками**.

На собесе: «Нули/константа плохи из‑за симметрии — нейроны учатся одинаково; для ReLU берут Kaiming; во фреймворке это уже по умолчанию».

Наглядно: прогон сигнала через 10 ReLU-слоёв при разном масштабе весов — [handbook_gl36_практика.ipynb](./practice/handbook_gl36_практика.ipynb) §36.5 (как на [сайте](https://mlhandbook-production.up.railway.app/parts/deep-learning/dl-optimization.html#36-5)).

### 1.4. Batch Normalization (BatchNorm) — нормализация внутри сети *(handbook §36.3)*

> **Не путать с регуляризацией «против зубрёжки».** Главное у BN — чтобы `h` / `z = W·h` не скакали по масштабу и обучение не разваливалось. В лекции DLS BN стоит в блоке Regularization рядом с Dropout; канонический разбор — **здесь** (гл. 36). В [d.4.37](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md) — хвост §37.6; эффект «чуть меньше переобучения» — побочный.

Числовой разбор «зачем, если h раздулся» (W¹, h, W², градиенты) → [d.4.36.1](./d.4.36.1%20Пример%20—%20зачем%20BatchNorm.md).  
Практика PyTorch → [pytorch/16](../../../../pytorch/pytorch%20дубинин/16/16_batchnorm.ipynb). Handbook-код → [handbook_gl36_практика.ipynb](./practice/handbook_gl36_практика.ipynb) §36.3, §36.6.

**BatchNorm** — нормализация **внутри сети** по мини-батчу: вычесть μ, поделить на σ по батчу, затем масштаб обучаемыми **γ** и **β**.

##### С нуля: нейрон, батч, где тут BN (чтобы не путаться)

**1 объект, 1 нейрон.** Признаки `x` (например 3 числа) → один нейрон → **одно** число `h`.  
Сколько `h` — это число **нейронов**, не число признаков: 3 признака и 1 нейрон → один `h`; 3 признака и 5 нейронов → пять `h`.

**Слой 2** (упрощённо один выход) считает, например:

$$
\Large
\hat{y} = h \cdot W^{2} + b^{2}
$$

Если `W²` тот же и `h` внезапно вырос — `ŷ` тоже вырастет. Веса **каждого нейрона** в слое **общие** на все объекты батча: один набор `w, b` у нейрона на все квартиры, а не «свой W на каждую квартиру».

**Батч из 4 объектов, всё ещё 1 нейрон.** Тот же нейрон (одни веса) пробегает по 4 квартирам → **4 числа** `h`, например 2, 4, 6, 8.

| путаница | как правильно |
| --- | --- |
| «4 числа = 4 нейрона» | нет: **1 нейрон × 4 объекта** |
| «разные `h` в батче — плохо» | нет: разные квартиры → разные `h` и разные `ŷ` — **норма** |
| «BN делает квартиры одинаковыми» | нет: после нормировки числа **всё ещё разные**, только громкость стандартная |

**3 нейрона × 4 квартиры.** Получается матрица `h` формы `(4, 3)` — всего 12 чисел. BatchNorm **не** нормализует все 12 одной кучей. Для **каждого нейрона отдельно**: нейрон A — свои 4 числа по квартирам; B — свои 4; C — свои 4.

```
квартиры ↓ \ нейроны →     A      B      C
        квартира 1        hA1    hB1    hC1
        квартира 2        hA2    hB2    hC2
        квартира 3        hA3    hB3    hC3
        квартира 4        hA4    hB4    hC4
                              ↑
                    BN смотрит вниз по столбцу
                    (по батчу, внутри одного нейрона)
```

**В чём тогда проблема без BN?** Не в том, что в одном батче `h` разные.  
Проблема **между шагами обучения**: оба слоя обновляются каждый шаг. Слой 1 поменял веса → для **тех же** квартир весь масштаб `h` уехал (вчера ~2…8, сегодня ~20…80) → слой 2 со старым `W²` даёт кривые `ŷ` и снова чинит веса. Разные предсказания внутри батча при этом по-прежнему нужны; ломает **скачок общей громкости**.

> Аналогия: готовишься к экзамену, а программу экзамена каждую неделю меняют.

**Зачем BN даже «на одном нейроне».** Чтобы общий диапазон/`громкость` его `h` по батчу держался стабильным от шага к шагу — общим весам слоя 2 легче. Разные `ŷ` у разных квартир остаются.

На **одном** объекте без батча BN на train почти бессмысленен (не из чего честно оценить μ/σ). Батч — инструмент статистики, не «причина ставить BN».

##### Формула и пример

**Решение.** Перед следующим слоем выходы нейрона приводим к стандартному масштабу — как нормализация входа в [`d.4.37` §1](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md), только **по текущему батчу** (и **по этому нейрону**):

$$
\Large
\hat{x} = \frac{x - \mu_{\mathrm{batch}}}{\sqrt{\sigma^{2}_{\mathrm{batch}} + \varepsilon}}, \qquad y = \gamma\hat{x} + \beta
$$

В следующий слой идёт обычно уже **`y`** (после γ, β), не сырой `h`.

**Пример.** Батч из 4 объектов, один нейрон выдал: 2, 4, 6, 8.

1. Среднее μ = 5. Дисперсия σ² = (9 + 1 + 1 + 9)/4 = 5, std ≈ 2.24.
2. Нормируем: x̂ = (−1.34, −0.45, 0.45, 1.34) — среднее 0, разброс 1; **квартиры по-прежнему различаются**.
3. Масштаб и сдвиг: при γ = 2, β = 1 → y = 2·x̂ + 1 = (−1.68, 0.1, 1.9, 3.68).

**γ и β — обучаемые.** Нормировка сначала сбрасывает хаос масштаба; γ, β дают **управляемый** масштаб (не обязанность «вернуть как было»). Если сети нужно, она может выучить γ ≈ 2.24, β ≈ 5 — и получить обратно примерно (2, 4, 6, 8). В худшем случае сеть BN «отменит»; часто γ≈1, β≈0 — почти оставляют стандартный вид. В работе формулы γ/β руками не крутят — важно знать, что они есть и учатся (`bn.weight`, `bn.bias`).

**На inference** батча может не быть (пришла одна картинка). Тогда берут μ и σ², накопленные скользящим средним за время обучения.

Что даёт:

- обучение **быстрее и стабильнее**;
- можно брать больший learning rate — потому что шаг = α · градиент, а градиенты больше не скачут на порядки (без BN приходится держать маленький α «на всякий случай»). Подробно → [`d.4.36.1` §3.2](./d.4.36.1%20Пример%20—%20зачем%20BatchNorm.md);
- небольшой побочный регуляризующий эффект (статистика батча — немного шума) — см. [`d.4.37` handbook §37.6](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md#batchnorm-handbook-376--здесь-только-хвост).

На train и eval BatchNorm ведёт себя по-разному → тоже нужны `model.train()` / `model.eval()`.  
Не «чтобы не подсматривать в ответы», а чтобы на тесте выключить train-режим: BatchNorm берёт накопленные μ/σ, Dropout перестаёт гасить нейроны.

**Минусы / нюансы на практике** (курс Дубинина + PyTorch):

1. **BN и Dropout на один слой** — лучше не вместе: ошибки не будет, но обычно толку мало / мешают друг другу.
2. **Маленький batch** (примерно 3–5) — на train BN считает μ и σ **по текущему батчу**. Если объектов мало, эти оценки почти случайные: один «странный» пример сильно сдвигает среднее → нормировка дёрганая → следующий слой снова видит шумный масштаб. На большем батче (десятки+, от ~8 уже лучше) статистика стабильнее. В задаче размер batch всё равно проверяют по val. (Маленький batch сам по себе иногда любят из‑за шума SGD / памяти — но это плюс для оптимизатора, минус именно для BN.)
3. **По-разному на train и val** — см. выше: без `eval()` на тесте будут batch-статистики вместо накопленных → предсказания кривые.
4. У `Linear`, к которому цепляют BN, часто ставят **`bias=False`**: сдвиг уже даёт β у BatchNorm, bias Linear почти дублирует его.
5. BN **не всегда** лучше «просто так»: крошечная сеть + крошечный batch — часто оверкилл; смотри val.

**Короткий чеклист «я понял BN»**

1. 1 нейрон на 1 объект → одно `h`; в батче из N → N чисел у этого нейрона.  
2. Разные `h`/`ŷ` внутри батча — норма; проблема — скачок **громкости** между шагами.  
3. BN нормализует **по батчу внутри одного нейрона**, не смешивая все нейроны.  
4. Веса общие; после BN в слой 2 идёт `y = γ·x̂+β`.  
5. `train`/`eval`, не крошечный batch, лучше не с Dropout на один слой.

На собесе: «Dropout — против переобучения; BatchNorm — стабильность и скорость сходимости (плюс побочный регуляризующий эффект)».

## 2. Градиентная оптимизация в DL *(лекция)*

### 2.1. Общая петля (как в классике)

```
батч → forward → loss → zero_grad → backward (autograd) → шаг оптимизатора по всем W, b
```

Один проход по (почти) всем данным = **эпоха**.

В коде PyTorch перед `backward` обычно вызывают `optimizer.zero_grad()`: `.grad` **накапливается**, а не перезаписывается. Иначе следующий батч «приедет» поверх старого градиента. Подробнее — [`d.4.35` §11.2](../d.4.35%20Backpropagation/d.4.35%20Backpropagation.md#зачем-ещё-optimizerzero_grad-деталь-pytorch-не-математика-спуска) (абзац про `zero_grad`).

**Оптимизатор** — это правило «как именно сдвинуть веса, зная градиент». Самое простое правило — SGD. Остальные — его улучшения.

### 2.2. SGD — базовый шаг

То же правило, что в [d.0](../../d.0%20Градиент%20и%20правило%20цепочки.md#84-почему-раньше-цепочки-не-было-видно):

$$
\Large w \leftarrow w - \alpha \cdot \nabla_w L
$$

α — **learning rate**: множитель, который выбираем сами. Сам **шаг = α · ∇L** — то, что вычитаем из веса.

#### Как градиент двигает вес (база для всего §2)

1. **Сдвиг веса пропорционален градиенту.** Вес меняется на α · градиент: чем больше градиент по модулю, тем сильнее сдвиг (при том же α).

   | градиент | сдвиг при α = 0.01 |
   | --- | --- |
   | 2 | −0.02 |
   | 10 | −0.10 |
   | 100 | −1.00 |

2. **Слишком большой сдвиг вредит.** Вес может перелететь минимум, и тогда лосс вырастет. Или вес начнёт метаться туда-сюда, а лосс будет «скакать».
3. **α сдерживает шаг.** Градиент говорит, *куда* двигать вес и насколько сильно этого «хочет» лосс. α решает, *насколько далеко* шагнуть за один раз.

| Ситуация | Что происходит |
| --- | --- |
| градиент большой, α нормальный | шаг умеренный — ок |
| градиент большой, α тоже большой | вес улетает, лосс скачет или взрывается |
| градиент маленький | вес почти не двигается — учимся медленно |

Все улучшения ниже (Momentum, Adagrad, RMSProp, Adam) решают именно эту проблему: как сделать шаг **не слишком большим и не слишком маленьким** для каждого веса.

Градиент считают не по всей выборке (дорого), а по **батчу** — пачке из 32–256 объектов. Это и есть стохастический градиентный спуск (SGD).

#### Как из многих объектов получается один шаг (формулы со слайда)

$$
\Large
L(W) = \frac{1}{N}\sum_{i=1}^{N} L_i(x_i, y_i, W)
\qquad
\nabla_W L(W) = \frac{1}{N}\sum_{i=1}^{N} \nabla_W L_i(x_i, y_i, W)
$$

- верхняя: **средний лосс** по объектам — насколько плохо сейчас (одно число, по нему смотрят график, веса им не двигают);
- нижняя: **средний градиент** по объектам — куда крутить веса;
- ∇_W L — это dL/dW, не умножение (как читать — [`d.0` §3.1](../d.0%20Градиент%20и%20правило%20цепочки.md#31-запись--набла--то-же-dldw-другой-шрифт)).

Сумма Σ (от i = 1 до N) идёт **по объектам**, не по весам.

**Пример: один вес, 4 объекта.** Модель ŷ = w · x, стоим в w = 1.

На каждом объекте:

$$
\Large
L_i = (w x_i - y_i)^2,
\qquad
\nabla_w L_i = 2(w x_i - y_i)\cdot x_i
$$

| i | x | y | ŷ = w·x | ошибка ŷ − y | Lᵢ | ∇Lᵢ = 2·ошибка·x |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | 2 | 1 | −1 | 1 | 2·(−1)·1 = **−2** |
| 2 | 2 | 4 | 2 | −2 | 4 | 2·(−2)·2 = **−8** |
| 3 | 1 | 3 | 1 | −2 | 4 | 2·(−2)·1 = **−4** |
| 4 | 1 | 0.5 | 1 | +0.5 | 0.25 | 2·(0.5)·1 = **+1** |

Каждый объект «хочет» своего: объекты 1–3 тянут w вверх (градиент −), объект 4 — вниз (+). За один шаг нельзя сдвинуть вес четырьмя разными способами, поэтому усредняем.

Средний лосс (верхняя формула):

$$
\Large L = \frac{1 + 4 + 4 + 0.25}{4} = 2.3125
$$

Средний градиент (нижняя формула):

$$
\Large \nabla_w L = \frac{(-2) + (-8) + (-4) + 1}{4} = \frac{-13}{4} = -3.25
$$

Шаг (α = 0.1):

$$
\Large w \leftarrow 1 - 0.1 \cdot (-3.25) = 1 + 0.325 = 1.325
$$

Градиент отрицательный → вес растёт, к минимуму.

**Если весов несколько.** У каждого объекта градиент — уже **вектор** (по числу на каждый вес). Усредняем векторы **поэлементно**: первые компоненты с первыми, вторые со вторыми:

$$
\Large \frac{(-2,\,-4) + (-8,\,-2) + (-4,\,-1) + (1,\,0.5)}{4} = \left(\frac{-13}{4},\ \frac{-6.5}{4}\right) = (-3.25,\ -1.625)
$$

Дальше каждому весу — своя компонента:

$$
\Large w_1 \leftarrow w_1 - \alpha \cdot (-3.25)
$$

$$
\Large w_2 \leftarrow w_2 - \alpha \cdot (-1.625)
$$

Итого порядок:

1. объекты → у каждого свой Lᵢ и свой ∇Lᵢ;
2. **усреднили по объектам** (нижняя формула) → один ∇L батча;
3. **раздали по весам**: каждый вес сдвигается на α · свою компоненту ∇L.

**Почему маленький батч шумит — на тех же числах.** Если батч = только объект 4, градиент +1 → w = 1 − 0.1 · 1 = 0.9: шаг **не туда**. Батч из объектов 2 и 3: (−8 − 4)/2 = −6 → w = 1 − 0.1 · (−6) = 1.6, рывок вдвое сильнее, чем по всем четырём. Чем меньше объектов в среднем, тем сильнее оно отличается от настоящего −3.25.

**Проблема: градиент по батчу «шумный».** Пусть по всей выборке градиент = **−6**. А по отдельным батчам получилось:

| батч | 1 | 2 | 3 | 4 | среднее |
| --- | --- | --- | --- | --- | --- |
| градиент | −14 | +2 | −9 | −3 | **−6** |

В среднем направление верное, но каждый отдельный шаг дёргается: то сильно вправо, то даже влево (+2). Чем меньше батч — тем сильнее шум.

Вторая беда — «овраг»: если лосс в одну сторону крутой, а в другую пологий, SGD скачет от стенки к стенке поперёк оврага и медленно ползёт вдоль него к минимуму.

Плюс SGD: простой, предсказуемый. Минус: на сложных лоссах DL медленный и капризный.

На лекции SGD улучшают **двумя идеями**.

### 2.3. Идея 1 — инерция (Momentum)

> Аналогия: шар катится с горки. На каждой кочке он не останавливается и не разворачивается — по инерции продолжает катиться туда, куда катился. Мелкие кочки (шум) почти не сбивают его с пути.

Вместо того чтобы шагать по **текущему** градиенту, копим «скорость» v — смесь прошлых градиентов:

$$
\Large v \leftarrow \beta v + \nabla_w L, \qquad w \leftarrow w - \alpha v
$$

β ≈ 0.9 — «сколько помним прошлое».

**Пример.** Градиенты скачут: 5, −3, 5, −3 (в среднем +1 — направление есть, но его не видно за шумом).

| шаг | градиент g | обычный SGD (α=0.1): сдвиг −α·g | momentum: v = 0.9·v + g |
| --- | --- | --- | --- |
| 1 | 5 | −0.5 | 0.9·0 + 5 = **5** |
| 2 | −3 | +0.3 (откат назад!) | 0.9·5 − 3 = **1.5** |
| 3 | 5 | −0.5 | 0.9·1.5 + 5 = **6.35** |
| 4 | −3 | +0.3 (снова назад) | 0.9·6.35 − 3 = **2.715** |

SGD топчется: вперёд-назад-вперёд-назад. У momentum v **всегда одного знака** — сеть стабильно идёт в верном направлении, шум гасится.

**Минусы Momentum**

1. **Проскакивает минимум.** Скорость накоплена — у дна шар по инерции катится дальше, потом разворачивается и какое-то время колеблется. Пример: после шага 3 в таблице v = 6.35, а вес уже у минимума (градиент ≈ 0). Тогда следующее v ≈ 0.9 · 6.35 + 0 = 5.7 — вес всё равно сдвинется на α · 5.7, хотя «надо стоять».
2. **Ещё один гиперпараметр β.** Слишком большое (0.99) — долго едет не туда после смены направления; слишком маленькое — шум почти не гасится. Обычно берут 0.9.
3. **Один α на все веса остаётся.** Проблему «громкого» и «тихого» веса Momentum не решает — для этого нужна идея 2 (§2.4). Поэтому Adam = Momentum + RMSProp.
4. **Запаздывает.** v — смесь прошлых градиентов, на резкую смену рельефа реагирует с задержкой.

**Nesterov momentum** — как раз чинит пункт 1: «сначала шагни по инерции, потом посмотри градиент в новой точке и поправься» (тормозит заранее, до проскока). Достаточно знать название.

### 2.4. Идея 2 — у каждого веса свой шаг (Adagrad → RMSProp)

**Проблема.** У SGD один α на **все** веса. Но веса бывают разные:

- вес w₁ умножается на частый/крупный признак → градиенты большие, например 10 → при обычном SGD этот вес **скачет**;
- вес w₂ умножается на редкий/мелкий признак → градиенты маленькие, например 0.1 → этот вес почти **не двигается**.

(Градиент по весу пропорционален своему признаку: dL/dw = 2(ŷ − y) · x, см. `d.0`. Крупный x → крупный градиент.)

При α = 0.01: шаг w₁ = 0.01·10 = **0.1**, шаг w₂ = 0.01·0.1 = **0.001**. Второй вес почти не учится. Увеличишь α для него — первый начнёт «перелетать».

Это прямое следствие правила из §2.2: сдвиг = α · градиент. «Громкий» вес с большим градиентом прыгает и раскачивает лосс, «тихий» почти стоит. Один α на всех не подходит.

> Аналогия: громкий крикун и тихий шёпот. Adagrad приглушает крикуна и усиливает шёпот, чтобы обоих было слышно одинаково.

#### Adagrad: делим шаг на «сколько этот вес уже трясло»

Для каждого веса копим сумму квадратов его градиентов (cache) и делим шаг на корень из неё:

$$
\Large \text{cache} \leftarrow \text{cache} + g^2, \qquad w \leftarrow w - \alpha \frac{g}{\sqrt{\text{cache}} + \varepsilon}
$$

ε — крошечное число, чтобы не делить на ноль.

**Пример (первый шаг, α = 0.01):**

| вес | g | cache = g² | шаг = α · g / √cache |
| --- | --- | --- | --- |
| w₁ | 10 | 100 | 0.01 · 10 / 10 = **0.01** |
| w₂ | 0.1 | 0.01 | 0.01 · 0.1 / 0.1 = **0.01** |

Шаги **выровнялись**: и «громкий», и «тихий» вес теперь двигаются одинаково заметно.

**Минус Adagrad:** cache только **растёт**. Почему?

Формула: `cache ← cache + g²`. Это **сумма**: каждый раз прибавляем новый квадрат градиента и **ничего не вычитаем**.  
g² всегда ≥ 0 (квадрат), поэтому cache не может уменьшиться — только стоит или растёт.

Пример: g = 10 каждый раз → каждый раз прибавляем g² = 100:

| итерация | что делаем | cache | √cache | размер шага α·10/√cache |
| --- | --- | --- | --- | --- |
| 1 | 0 + 100 | 100 | 10 | 0.01 · 10/10 = **0.01** |
| 2 | 100 + 100 | 200 | ≈14.1 | ≈0.007 |
| 4 | … + 100 ещё раз | 400 | 20 | 0.01 · 10/20 = **0.005** |
| 100 | суммировали 100 раз по 100 | 10 000 | 100 | 0.01 · 10/100 = **0.001** |

Знаменатель √cache всё больше → шаг всё меньше → сеть почти перестаёт учиться (шаг «затухает»), даже если градиент всё ещё 10.

#### RMSProp: помнить только недавнее

Чиним затухание: cache = **скользящее среднее** квадратов, старое постепенно забывается (ρ ≈ 0.9):

$$
\Large \text{cache} \leftarrow \rho \cdot \text{cache} + (1 - \rho)\, g^2
$$

Тот же g = 10 каждый раз (ρ = 0.9): cache растёт 10 → 19 → 27.1 → … и **останавливается около 100** (= g²). Шаг держится около 0.01 · 10/10 = 0.01 и не затухает.

Почему останавливается: каждый шаг cache **на 90%** старое + **на 10%** новое g². Когда cache уже ≈ 100, а g² = 100:

`0.9 · 100 + 0.1 · 100 = 100` — прибавили столько же, сколько «забыли». Равновесие. Дальше cache не растёт.

> Аналогия: Adagrad помнит **все** обиды за всю жизнь и становится всё осторожнее. RMSProp помнит только последние — осторожен, когда реально трясёт, и смелеет, когда успокоилось.

### 2.5. Adam = Momentum + RMSProp — рабочий дефолт

**Adam** объединяет обе идеи:

- от Momentum — **инерция** (скользящее среднее самих градиентов) → меньше шума;
- от RMSProp — **свой шаг каждому весу** (скользящее среднее квадратов) → тихие и громкие веса учатся одинаково.

Плюс небольшая поправка на первые шаги (bias correction): средние стартуют с нуля и в начале занижены — поправка их «досчитывает». Формулу учить не нужно.

| Метод | Идея одной строкой |
| --- | --- |
| SGD | шаг −α·g |
| Momentum | + инерция из прошлых шагов |
| Adagrad | свой шаг каждому весу; со временем затухает |
| RMSProp | Adagrad со скользящим средним — не затухает |
| **Adam** | **Momentum + RMSProp** |
| **AdamW** | Adam + правильный **weight decay** (§3.1) |

Есть и другие (Adadelta и т.п., даже оптимизаторы-нейросети), но на практике хватает этой линейки.

**Правило новичка / собеса:**

> Сомневаешься — **AdamW**, **`lr ≈ 3e-4`** (дефолт handbook для больших моделей / трансформеров). На маленьких MLP с лекции часто хватает **1e-3** — потом подстраиваешь.

```python
# рабочий старт (как на сайте ментора, gl.36.1)
opt = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=1e-2)
```

**Важно (слайд лекции):** даже у Adam/RMSProp **learning rate всё равно имеет значение**. «Адаптивный» — значит подстраивает шаги веса относительно друг друга, а общий масштаб всё равно задаёт α.

### 2.6. Learning rate: как выбрать и как менять

α **выбираем мы** (гиперпараметр). Сеть его не учит. Adam/RMSProp подстраивают шаги весов относительно друг друга, но общий масштаб всё равно задаёт α — поэтому его калибруют (и у Adam тоже).

| Что | Кто |
| --- | --- |
| стартовый α (0.001, 3e-4…) | ты / перебор гиперпараметров; в библиотеке есть дефолт, но это не «выбрал сам оптимизатор» |
| уменьшать α на плато (lr decay) | вручную или schedule (StepLR, ReduceLROnPlateau, cosine) |
| сеть меняет α через backprop | **нет** |

*(Слайд 21 лекции: слева — разный фиксированный α → разный график лосса; справа — на плато делают decay, и лосс снова падает.)*

#### Что бывает при разном α

Пример из [d.0](../../d.0%20Градиент%20и%20правило%20цепочки.md#84-почему-раньше-цепочки-не-было-видно): f(w) = w², стоим в w = 3, производная 2w = 6, минимум в w = 0.

α — learning rate (множитель), **шаг = α · g** (на сколько реально сдвинется вес).

| α (learning rate) | шаг = α·6 | w_новый = 3 − шаг | что случилось |
| --- | --- | --- | --- |
| 0.001 | 0.006 | 2.994 | сдвинулись на чуть-чуть — **ползём** вечность |
| 0.1 | 0.6 | 2.4 | нормальный шаг к нулю |
| 1.1 | 6.6 | −3.6 | **перелетели** минимум и оказались ещё дальше (3.6 от нуля, а было 3) → дальше будет ещё хуже, лосс взлетит |

#### Как по графику лосса понять, что с α

| Кривая train loss | Диагноз |
| --- | --- |
| взлетает / NaN | α **слишком большой** (перелетаем, как α = 1.1) |
| падает очень медленно, почти прямой линией | α **маленький** (ползём, как α = 0.001) |
| быстро упала и застряла высоко на плато | α великоват: прыгаем вокруг минимума, не можем в него попасть → уменьшить |
| быстро падает, потом плавно выходит на низкое плато | **ок** |

#### Learning rate schedule (lr decay) *(пробел ментора — закрываем)*

**Курс Дубинина:** [видео 11 — цикл обучения](https://www.youtube.com/watch?v=QZ-vKDAaThY) · [pytorch/11](../../../../pytorch/pytorch%20дубинин/11/11_цикл_обучения.ipynb) (ручной / фиксированный lr) · [видео 12 — LR_Scheduler](https://www.youtube.com/watch?v=oWevpnv3RI0) · [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb) · карта [0_как_учить_pytorch.md](../../../../pytorch/pytorch%20дубинин/0_как_учить_pytorch.md).

**Главная идея:** α (learning rate) **не обязан быть константой** на все эпохи. В процессе обучения им можно **управлять**: уменьшить вручную ([видео 11](https://www.youtube.com/watch?v=QZ-vKDAaThY), [pytorch/11](../../../../pytorch/pytorch%20дубинин/11/11_цикл_обучения.ipynb)) или через **scheduler** ([видео 12](https://www.youtube.com/watch?v=oWevpnv3RI0), [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb); `scheduler.step()` обычно раз в эпоху).

> Аналогия: паркуешься. Через весь город едешь быстро, а у парковочного места — медленно, по сантиметру. Если подъезжать к месту на скорости 60 — проскочишь.

Так и с α: в начале крупные шаги (быстро подойти к минимуму), в конце — мелкие (аккуратно в него попасть). Поэтому α **уменьшают** по ходу обучения.

Пример StepLR: α = 0.01 → на 10-й эпохе 0.001 → на 20-й 0.0001 (в коде — [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb) §1).

| Схема | Идея |
| --- | --- |
| `LambdaLR` | своя функция от номера шага → множитель к стартовому lr (демо «любое расписание») |
| `StepLR` | каждые N эпох умножить α на gamma |
| `MultiStepLR` | то же в выбранные эпохи (`milestones`) |
| `ExponentialLR` | на каждом `step()`: α *= gamma |
| `ReduceLROnPlateau` | лосс/метрика не улучшается `patience` эпох → уменьшить α |
| `CosineAnnealingLR` | α по **косинусу** от стартового до минимума за фиксированное число эпох — популярный decay в DL |
| warmup (+ cosine) | первые N шагов/эпох **плавно поднять** α от 0 (или малого) до рабочего; дальше cosine или step decay |

`StepLR` / `MultiStepLR` / `ExponentialLR` / `ReduceLROnPlateau` — разобраны в [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb). `LambdaLR` / cosine / warmup — в конспекте ниже; в курсе Дубинина отдельного видео нет.

#### Warmup и cosine *(handbook §36.4)*

**Постоянный α** на всём обучении — не лучший вариант. Типичная связка сейчас:

1. **Warmup** — в начале веса «сырые», градиенты шумные; резкий большой lr опасен. Первые ~сотни–тысячи шагов (зависит от задачи) α **плавно растёт** от нуля (или малого) до целевого, например `3e-4`.
2. **Decay** — после warmup α **снижают**: step/exponential или чаще **cosine** — вначале крупные шаги для скорости, в конце мелкие для доводки.

В PyTorch warmup часто делают через `LambdaLR` / `SequentialLR` (сначала линейный разгон, потом `CosineAnnealingLR`) или готовые рецепты в тренировочных скриптах. Идея и ручной decay — [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb).

На собесе: «warmup стабилизирует старт; cosine decay — плавное затухание lr к концу обучения».

**Связь с [видео 11](https://www.youtube.com/watch?v=QZ-vKDAaThY)** ([pytorch/11](../../../../pytorch/pytorch%20дубинин/11/11_цикл_обучения.ipynb)). Автор на регрессии: 50 эпох → **остановить** → руками новый Adam с меньшим lr → ещё эпохи. То же без остановки: например  
`MultiStepLR(opt, milestones=[50], gamma=0.1)` — на 50-й эпохе lr умножится сам ([pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb) §2).  
Если заранее не знаешь «на какой эпохе», удобнее `ReduceLROnPlateau` (снизит lr, когда val перестанет улучшаться; **`pytorch/12` §3**). Это как раз сценарий «уменьшил lr и **продолжил** на тех же весах» — см. абзац ниже; модель **не** учат с нуля.

В курсе Дубинина ([видео 12](https://www.youtube.com/watch?v=oWevpnv3RI0)) первый график у `LambdaLR` — часто график **самого lr по эпохам**, не лосса: видно, что расписание реально меняет шаг. «Больший lr быстрее роняет лосс, но риск перескока» — из таблицы про разные α выше, не из того графика.

На собесе: «lr schedule помогает дообучить, когда с фиксированным lr уже не ползёт».

**Практика:** [видео 12](https://www.youtube.com/watch?v=oWevpnv3RI0) · [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb).

#### Дообучить с меньшим lr или учить с нуля? *(чтобы не путать с подбором гиперпараметров)*

Два разных сценария — их часто смешивают.

| Ситуация | Что делать | Почему |
| --- | --- | --- |
| **Один прогон:** loss/метрика на плато, переобучения нет | **Уменьшить lr и продолжить** на тех же весах | Веса уже хорошие. Вручную ([видео 11](https://www.youtube.com/watch?v=QZ-vKDAaThY)) **или scheduler** (таблица выше: `MultiStepLR` / `StepLR` / `ReduceLROnPlateau`). Практика — [видео 12](https://www.youtube.com/watch?v=oWevpnv3RI0) · [pytorch/12](../../../../pytorch/pytorch%20дубинин/12/12_lr_scheduler.ipynb) |
| **Сравниваешь настройки** (другой стартовый lr, ширина сети, …) | Каждую конфигурацию **с нуля** | Иначе нечестное сравнение. Как в [d.2.4](../d.2%20Линейные%20модели%20метрические%20методы/d.2.4%20Главное%20из%20дз%20по%20KNN%20и%20лин%20классификатору.md) |
| Сильно поменял задачу/данные/архитектуру или после явного переобучения | Обычно **с нуля** (или чекпоинт «до порчи») | Старые веса заточены под другие условия |

Коротко:

- **снизить lr внутри одного обучения** = нормально (руками или scheduler) — **не** означает «учить модель заново»;
- **честно сравнить разные гиперпараметры** = каждый эксперимент с нуля.

#### Residual / skip-связи *(handbook §36.4)*

Приём из **ResNet**: выход блока **складывают с входом**:

$$
\Large y = x + F(x)
$$

где \(F(x)\) — то, что считает сам блок (свёртки, Linear+ReLU и т.д.). На **backward** градиент по \(x\) идёт **напрямую** через сложение («короткий путь»), минуя глубокий \(F\) — меньше **затухания градиента** в очень глубоких сетях. Поэтому возможны сотни слоёв и трансформеры.

Реализация residual-блока — [Deep-ML #113](https://www.deep-ml.com/problems/113), заготовка в [13_deep_ml_deep_learning.py](../../../../python_base/13_deep_ml_deep_learning.py). Архитектурные детали ResNet — отдельно, не в этом конспекте.

### 2.7. Что сказать на собесе про оптимизацию

1. Учим градиентным спуском по батчам (SGD); градиенты считает **autograd** (`loss.backward()`).  
2. SGD шумный → **Momentum** (инерция) и адаптивные методы (**Adagrad → RMSProp**, свой шаг каждому весу) → **Adam = Momentum + RMSProp**; на практике чаще **Adam/AdamW**.  
3. Даже для Adam важен **learning rate**; **warmup**, **cosine** (или другой) **schedule** — §2.6.  
4. Очень глубокие сети — **residual** \(y = x + F(x)\), иначе градиент гаснет — §2.6.  
5. Вход **нормализуем** (mean/std по train) — [d.4.37](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md) §1; числовой разбор одного шага → [d.4.37.1](../d.4.37%20Регуляризация%20в%20DL/d.4.37.1%20Пример%20—%20нормализация%20и%20один%20шаг%20обучения.md).  
6. **Следим за качеством** (train/val лосс и метрики) по ходу обучения — подробно в [d.4.37](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md#1-нормализация-входных-данных-пункт-лекции-data-normalization) §3.

### 2.9. AMP — Automatic Mixed Precision *(не было у Дубинина; дал ментор)*

Источник: [PyTorch AMP examples](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html). Практика: [pytorch/24_amp](../../../../pytorch/pytorch%20дубинин/24_amp/24_amp.ipynb).

#### Зачем простыми словами

Обычное обучение почти всё считает в **float32** — числа точные, но на большой модели (Transformer и т.п.) это:

- много **памяти GPU**;
- часто **медленнее**, чем можно.

**AMP** = «где можно — считай потоньше (`float16` / `bfloat16`), где опасно для точности — оставь `float32`».

Аналогия: считать сдачу в магазине можно на калькуляторе с 2 знаками после запятой (быстрее писать), а зарплату/налоги — с полной точностью. AMP сам решает, где какой «калькулятор».

Два инструмента — **не взаимоисключающие варианты**, а **пара в одном AMP-цикле**:

| инструмент | роль | когда в цикле |
| --- | --- | --- |
| `torch.autocast` | внутри `with` сам выбирает dtype для операций (часто forward+loss) | на forward + loss |
| `torch.amp.GradScaler` | временно **увеличивает** loss/градиенты, чтобы мелкие fp16-градиенты не стали 0, потом возвращает масштаб | на backward + step |

> **Не путай с «или/или».** Примеры 1 и 2 ниже разбирают каждый кусок **отдельно**, но на практике при классическом AMP (`float16` на GPU) их ставят **вместе**: сначала `autocast` (дешёвый forward), потом `GradScaler` (безопасный backward). Без `autocast` нет смешанной точности; без `scaler` при fp16 можно потерять мелкие градиенты. Для `bfloat16` scaler часто можно не включать — диапазон шире.

Важно: **веса** (`nn.Linear.weight`) обычно остаются **float32**. В тонком dtype считаются в основном **промежуточные вычисления** (активации, matmul) внутри `autocast`.

#### Пример 1. Что делает `autocast` (без обучения)
*(только про тонкий dtype на forward; scaler здесь ещё не нужен — обучения нет)*

Без AMP:

```text
x (float32) → Linear → y (float32)
```

С AMP:

```text
with autocast(...):
    x (float32) → Linear → y (часто float16/bfloat16)
```

Снаружи того же `with` тот же слой снова даёт float32.  
То есть autocast — не «перевёл всю сеть в fp16 навсегда», а «этот forward посчитай подешевле».

#### Пример 2. Зачем `GradScaler` (числа)
*(это не замена примеру 1, а вторая половина той же схемы: после autocast-forward)*

В float16 очень маленькое число может **округлиться в 0** (underflow).

Допустим, «честный» градиент веса = `1e-8` (`0.00000001`).

**Главное уточнение (часто путают):**  
этот градиент **один и тот же** и для float32, и для float16 — его считает математика сети / loss, а **не** «формат сам меняет величину градиента».

| формат | что происходит с тем же `1e-8` |
| --- | --- |
| **float32** | обычно **сохраняется** → `step` делает маленький, но ненулевой шаг |
| **float16 без scaler** | часто становится **0** → вес не двигается |
| **float16 + scaler** | временно ×scale → не ноль → перед `step` ÷scale → снова тот же `1e-8` |

| без scaler | с scaler (scale = 1024) |
| --- | --- |
| в fp16 `1e-8` → часто **0** | backward видит `1e-8 · 1024 = 1.024e-5` — уже не ноль |
| `optimizer.step` не двигает вес | перед step делим обратно: снова `1e-8` |

Не путай три разные вещи:

| что | смысл |
| --- | --- |
| **тонкий dtype (fp16)** | *формат* хранения/счёта (меньше бит). Не означает «градиент специально другой» |
| **величина градиента** | «насколько» менять вес — одна и та же «правда» задачи |
| **scale** | временно *домножить*, чтобы мелкое число не обнулилось в fp16, потом разделить обратно |

Ещё раз про шаг оптимизатора:

1. `backward` **не** меняет веса — только считает градиенты.  
2. Веса меняет `optimizer.step` (обычно веса и так **float32**).  
3. Перед `step` scaler возвращает не «другой формат весов», а **настоящий размер градиента**.  
4. Маленький шаг при маленьком градиенте — **нормально** (так же было бы и в fp32). Плохо, когда вместо маленького получается **ноль**.  
5. Нулевой градиент из‑за underflow ≠ «loss уже хороший». Loss может быть большим, просто сигнал «куда шагать» пропал.

**Картина целиком (AMP-цикл):**

1. **Forward (`autocast`)** — что можно, считаем/храним в лёгком dtype (быстрее, меньше памяти).  
2. **`scale(loss)`** — временно увеличили числа.  
3. **`backward`** — посчитали градиенты без обнуления мелких значений.  
4. **`unscale` + `step`** — вернули настоящую величину градиента → сдвинули float32-веса.

#### Типичный шаг (выучить порядок)

Без AMP ты уже писал:

```text
opt.zero_grad()
pred = model(x)
loss = loss_fn(pred, y)
loss.backward()
opt.step()
```

С AMP почти то же:

```text
opt.zero_grad()
with autocast(...):                 # 1) pred + loss в смешанной точности
    pred = model(x)
    loss = loss_fn(pred, y)
scaler.scale(loss).backward()       # 2) backward по УВЕЛИЧЕННОМУ loss
scaler.step(opt)                    # 3) unscale → opt.step (или skip при inf/NaN)
scaler.update()                     # 4) подстроить scale на следующий батч
```

`backward` обычно **не** кладут внутрь `autocast`: он идёт в тех dtype, которые forward уже выбрал.

#### Пример 3. Clipping + AMP *(дополнение, не ядро AMP)*

**Важно:** большой градиент бывает **не из‑за AMP** — взрыв возможен и на чистом float32.  
Ядро AMP — `autocast` + `GradScaler` (примеры 1–2). Их достаточно: перед `step` scaler сам вернёт нужный размер градиента.

**Clipping** — отдельный приём «градиент слишком большой → подрезать».  
Этот пункт только про связку: *если клипаешь и используешь AMP*, сначала `unscale_`, потом `clip`.

После `scale(loss).backward()` градиенты ещё ×scale. Если `max_norm=1.0`, а scale=1024:

- клипать сразу = резать **увеличенные** числа → порог бессмысленный;
- сначала `unscale_`, потом clip по «настоящим» градиентам.

```text
scale(loss).backward()
scaler.unscale_(optimizer)          # вернуть .grad к реальному масштабу
clip_grad_norm_(params, max_norm)   # теперь max_norm честный
scaler.step(optimizer)
scaler.update()
```

`unscale_` — **один раз** на optimizer за step.

**Практика:** сначала учи **без** clip. Если видишь взрывы / `NaN` / дикие скачки loss — тогда добавляй.  
В готовых рецептах больших моделей (часто NLP/Transformer) clip уже бывает в паттерне — там просто копируешь порядок `unscale_ → clip → step`. Слепо везде с маленьким `max_norm` не обязательно: можно и подрезать нормальные градиенты.

#### Пример 4. Accumulation (батч не влезает)

Хочешь effective batch = 32, а в память лезет только 16 → K=2 микробатча:

```text
loss = loss / 2
scaler.scale(loss).backward()   # микробатч 1, градиенты копятся
scaler.scale(loss).backward()   # микробатч 2
scaler.step(opt)                # один шаг
scaler.update()
```

Пока копим — **не** вызывай `update` (и `unscale_` — только перед финальным `step`).

#### Что запомнить / собес

- AMP нужен на **больших моделях + GPU** (NLP/трансформеры); на маленьком CPU почти без выигрыша — учишь API.
- `GradScaler` важен для **`float16`**; для `bfloat16` часто можно без него (диапазон шире).
- На собесе: *«AMP = autocast + GradScaler; forward в смешанной точности, градиенты масштабируем, чтобы не было underflow в fp16»*.

## 6. Словарь (оптимизация)

| Слово | Простыми словами |
| --- | --- |
| инициализация | стартовые значения весов; случайные, не нули |
| learning rate (α) | множитель перед градиентом; шаг = α · градиент |
| SGD | шаг −α·градиент по батчу |
| momentum | инерция: шагаем по накопленной «скорости», а не по одному градиенту |
| Adagrad / RMSProp | свой шаг каждому весу (Adagrad затухает, RMSProp нет) |
| Adam / AdamW | Momentum + RMSProp; дефолт в DL |
| lr schedule / decay | уменьшать α по ходу обучения |
| warmup | в начале плавно разогнать α |
| cosine decay | α по косинусу к низкому значению |
| residual (skip) | y = x + F(x); короткий путь градиента |
| BatchNorm / LayerNorm | нормализация внутри сети (батч vs один объект) |
| AMP / autocast | смешанная точность: часть ops в fp16/bf16 |
| GradScaler | масштабирует loss/grads против underflow в fp16 |
| седловая точка | градиент ≈ 0, но это не минимум; SGD может застрять |

Нормализация входа — в словаре [d.4.37](../d.4.37%20Регуляризация%20в%20DL/d.4.37%20Регуляризация%20в%20DL.md#1-нормализация-входных-данных-пункт-лекции-data-normalization).
