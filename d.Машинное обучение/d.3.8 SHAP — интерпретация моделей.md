## 1. Зачем интерпретировать предсказания

Хорошая модель — это **не только** высокая метрика, но и **понимание**, *почему* она так решила.

**Два примера из статьи:**

- Модель предсказала, что клиент **склонен купить товар**. Если мы знаем, **что именно** повлияло на покупку, мы можем выстроить стратегию, направленную на повышение продаж.
- Модель предсказала, что пациент **скоро заболеет**. Точность таких прогнозов невысока (много скрытых от модели факторов), но **объяснение причин** помогает врачу обратить внимание на новые симптомы.

**Вывод:** интерпретация **расширяет границы применения** модели, особенно когда её точность сама по себе не слишком высока.

> С линейными моделями всё просто: чем больше абсолютное значение коэффициента при предикторе, тем он важнее. Но объяснить важность фичей **градиентного бустинга** (сотни деревьев) — заметно сложнее. Именно для этого и нужен **SHAP**.

## 2. Что не так с обычной Feature Importance

В `sklearn`, `xgboost`, `lightgbm` есть **встроенные** меры важности для «деревянных» моделей:

| Метрика | Что показывает | Как считается |
|:---|:---|:---|
| **Gain** | относительный вклад фичи в модель | идём по каждому узлу каждого дерева, смотрим, какая фича разбивает узел и **насколько снижает неопределённость** (Gini impurity, information gain); суммируем вклад по всем деревьям |
| **Cover** | количество наблюдений, прошедших через узлы с этой фичей | сумма наблюдений во всех узлах фичи. Пример: 4 фичи, 3 дерева; фича 1 в узлах содержит 10, 5, 2 наблюдения → важность $= 10+5+2 = 17$ |
| **Frequency** | как часто фича встречается в узлах | суммарное число разбиений дерева по этой фиче во всех деревьях |

### Главная проблема

> Все эти меры говорят, **насколько** фича важна, но **не говорят, КАК** она влияет на предсказание.

**Пример из статьи.** Мы узнали, что **уровень дохода** важен для оценки платёжеспособности клиента банка. Но:

- **Как именно** он влияет?
- **Насколько сильно** более высокий доход смещает предсказание?

Можно было бы сделать несколько предсказаний, меняя доход. Но **что делать с остальными фичами**? Нам нужно влияние дохода **независимо** от других фичей — при их **некотором среднем значении**. Этакий «среднестатистический клиент банка в вакууме».

Тут и приходит на помощь **SHAP**.

## 3. Идея SHAP: значения Шэпли

Название расшифровывается как **SH**apley **A**dditive ex**P**lanations. В основе — **значения Шэпли** (по имени американского математика Ллойда Шэпли), придуманные в **теории игр**.

### Аналогия с карточной игрой

Группа людей играет в карты. **Как распределить призовой фонд** между ними в соответствии с **вкладом** каждого?

**Допущения (из статьи):**

1. Сумма вознаграждений всех игроков равна **общему призовому фонду**.
2. Если два игрока сделали **равный вклад** — они получают **равную награду**.
3. Если игрок **не внёс вклада** — он **не получает** вознаграждения.
4. Если игрок провёл **две игры** — его суммарное вознаграждение равно **сумме** вознаграждений за каждую игру.

**Как это связано с моделью:**

- **Игроки** = **признаки (фичи)** модели.
- **«Призовой фонд»** = **предсказание** модели.
- **Вклад игрока** = **вклад фичи** в предсказание.

То есть SHAP «честно» делит предсказание между фичами по их вкладу.

### Формула значения Шэпли

Для фичи $i$ её вклад усредняется по **всем возможным коалициям** $S$ из остальных фичей:

$$
\phi_i = \sum_{S \subseteq N \setminus {i}} \frac{|S|!\,(n - |S| - 1)!}{n!}\,\big(p(S \cup {i}) - p(S)\big)
$$

**Расшифровка:**

| Обозначение | Что это |
|:---|:---|
| $N$ | множество **всех** фичей (все «игроки»), $n = \lvert N \rvert$ |
| $S$ | подмножество (коалиция) фичей, **не содержащая** $i$ |
| $p(S)$ | предсказание модели, когда **известны** значения только фичей из $S$, а остальные — **неизвестны (NULL)** |
| $p(S \cup {i}) - p(S)$ | **маргинальный вклад** фичи $i$: насколько меняется предсказание, если к коалиции $S$ добавить фичу $i$ |
| $\dfrac{\lvert S\rvert!\,(n-\lvert S\rvert-1)!}{n!}$ | **вес** коалиции: чем больше фичей в $S$ и чем их больше всего ($n$), тем меньше вес |
| $\phi_i$ | итоговое **значение Шэпли** фичи $i$ (её вклад) |

> **Смысл:** мы **не доверяем** какому-то одному порядку добавления фичей, а **усредняем** вклад $i$ по **всем** возможным коалициям $S$. Так получается «честная» (единственно возможная при этих требованиях) оценка вклада.

### Свойство аддитивности

Главное удобство SHAP — предсказание **раскладывается в сумму** вкладов:

$$
f(x) = \phi_0 + \sum_{i=1}^{n} \phi_i(x)
$$

где:

- $f(x)$ — предсказание модели для объекта $x$;
- $\phi_0 = p(\varnothing)$ — **базовое значение** (base value): предсказание, когда **все** фичи неизвестны (среднее по датасету);
- $\phi_i(x)$ — вклад $i$-й фичи (значение Шэпли) **для конкретного объекта** $x$.

**Проверка (см. пример ниже):** сумма вкладов **точно** сходится к предсказанию — ни один «кусок» не теряется и не появляется лишний.

### Как считать на практике

Точное вычисление суммы по **всем** коалициям имеет сложность $O(2^n)$ — для 50 фичей это нереально. Поэтому в библиотеке `shap` используются **алгоритмы оптимизации** (подробнее — на GitHub библиотеки):

- **TreeExplainer** — точный и быстрый расчёт для деревьев (XGBoost / LightGBM / CatBoost / sklearn);
- **LinearExplainer** — для линейных моделей;
- **DeepExplainer** — для нейросетей;
- **KernelExplainer** — универсальный (для любой модели), но медленный, приближает значения Шэпли.

## 4. Ручной пример «Bobby» (ванильный пример XGBoost)

Возьмём пример из документации XGBoost, который разбирает статья.

**Задача:** предсказать, **нравятся ли человеку компьютерные игры**.

**Фичи:** всего две:

- **age** — возраст;
- **gender** — пол ($0$ или $1$).

**Объект:** **Bobby** — маленький мальчик, попавший в **самый левый узел** дерева.

**Цель:** посчитать **значение Шэпли для фичи** `age`.

### Какие бывают коалиции

Фич всего $n = 2$, поэтому для фичи `age` возможны всего **два** набора $S$ (без неё):

- $S = {}$ — *нет фичей*;
- $S = {\text{gender}}$ — *есть только пол*.

### Случай 1: наборов фичей нет ($S = {}$)

Разные модели по-разному работают, когда значений фичей нет (все равны `NULL`). Договоримся (как в статье), что **модель усредняет предсказание по веткам дерева**.

- **Без фичей:** предсказание $p(\varnothing)$.
- **Добавили возраст:** предсказание $p({\text{age}})$.
- Их **разница в примере равна 1.025**.

Тогда вклад этого случая:

$$
\frac{|S|!\,(n-|S|-1)!}{n!}\,\big(p(S\cup{i}) - p(S)\big)
= \frac{1\,(2-0-1)!}{2!}\,(1.025) = 0.5125
$$

**Проверка веса:** $(2-0-1)! = 1! = 1$, $\;2! = 2$, значит $\frac{1 \cdot 1}{2} = 0.5$. И $0.5 \times 1.025 = 0.5125$. ✅

### Случай 2: знаем пол ($S = {\text{gender}}$)

Для Bobby предсказание **без возраста, только с полом**:

$$
p({\text{gender}}) = \frac{\tfrac{2 + 0.1}{2} + (-1)}{2} = 0.025
$$

**Что тут происходит:** с известным полом и **неизвестным** возрастом модель **усредняет по веткам возраста** (получается $\tfrac{2+0.1}{2}$), прибавляет вклад второго дерева $(-1)$ и **усредняет по деревьям** (делит на $2$).

Теперь **добавим возраст** — предсказание станет равно значению **самого левого дерева**, то есть $p({\text{age}, \text{gender}}) = 2$.

Разница:

$$
p({\text{age}, \text{gender}}) - p({\text{gender}}) = 2 - 0.025 = 1.975
$$

Вклад этого случая:

$$
\frac{|S|!\,(n-|S|-1)!}{n!}\,\big(p(S\cup{i}) - p(S)\big)
= \frac{1\,(2-1-1)!}{2!}\,(1.975) = 0.9875
$$

**Проверка веса:** $(2-1-1)! = 0! = 1$, $\;2! = 2$, значит $\frac{1 \cdot 1}{2} = 0.5$. И $0.5 \times 1.975 = 0.9875$. ✅

### Суммируем

Итоговое значение Шэпли для фичи `age` у Bobby:

$$
\phi_{\text{Age Bobby}} = 0.9875 + 0.5125 = 1.5
$$

> **Как это читать:** фича `age` **увеличивает** предсказание Bobby на **1.5** относительно базового значения. Причём это вклад **для конкретного объекта** (Bobby), а не усреднённая глобальная важность. Именно это и есть главное отличие SHAP от обычной Feature Importance.

## 5. Визуализации SHAP

Библиотека `shap` даёт богатый функционал визуализации — «объяснить модель как для бизнеса, так и для самого аналитика, чтобы оценить адекватность модели».

**Реальный кейс из статьи:** анализ **оттока сотрудников** из компании, модель — **XGBoost**.

### 5.1. Summary plot (важность + направление)

Код из статьи:

```python
import shap

shap_test = shap.TreeExplainer(best_model).shap_values(df)
shap.summary_plot(shap_test, df,
                  max_display=25, auto_size_plot=True)
```

**Как читать:**

- значения **слева** от центральной вертикальной линии — это **negative** класс ($0$), **справа** — **positive** ($1$);
- чем **толще** линия — тем **больше** таких точек наблюдения;
- чем **краснее** точки — тем **выше** значение фичи в этой точке.

**Выводы из графика (из статьи):**

- чем **меньше** сотруднику повышают зарплату → тем **выше** вероятность его ухода;
- есть **регионы офисов**, где отток выше;
- чем **моложе** сотрудник → тем выше вероятность ухода.

Можно сразу собрать **портрет уходящего сотрудника**: ему не повышали зарплату, он достаточно молод, холост, долгое время на одной позиции, не было повышений грейда, не было высоких годовых оценок, он стал мало общаться с коллегами.

### 5.2. Force plot (объяснение одного предсказания)

Показывает, **как фичи «толкают» предсказание** конкретного объекта от **базового значения** к **итоговому** (одни — в плюс, другие — в минус). Это и есть наглядная иллюстрация аддитивности:

$$
f(x) = \phi_0 + \sum_i \phi_i
$$

### 5.3. Dependence plot (зависимость от фичи)

2D-график зависимости **вклада фичи** от её значения. Видно, **как именно** (линейно / порогом / нелинейно) фича влияет на предсказание. Это ровно тот вопрос, на который обычная Feature Importance ответить не могла.

### 5.4. Объяснение нейросетей на картинках

`shap` умеет визуализировать и предсказания **нейронных сетей** — подсвечивая на изображении пиксели, повлиявшие на результат.

## 6. SHAP vs Feature Importance — в чём разница

| Критерий | Feature Importance (`Gain` / `Cover` / `Frequency`) | SHAP |
|:---|:---|:---|
| **Что показывает** | **насколько** фича важна (усреднённо) | **как и насколько** влияет; **вклад каждой фичи** |
| **Направление влияния** | ❌ нет | ✅ есть (плюс/минус, знак $\phi_i$) |
| **Уровень** | **глобальный** (одно число на фичу для всей модели) | **локальный** (для **каждого** объекта) + агрегируется в глобальный |
| **Влияние «в вакууме»** | нет | ✅ вклад фичи **независимо** от других (усреднение по коалициям) |
| **Аддитивность** | — | ✅ $f(x) = \phi_0 + \sum \phi_i$ точно восстанавливает предсказание |
| **Теория** | эвристика | строгие **значения Шэпли** (теория игр) |
| **Скорость** | очень быстро (бесплатно при обучении) | для деревьев быстро (`TreeExplainer`), для любой модели медленно (`KernelExplainer`) |
| **Тип модели** | только «деревянные» | **любая** модель |

**Простыми словами:**

- **Feature Importance** отвечает на вопрос «**какие** фичи вообще важны для модели?»
- **SHAP** отвечает на вопрос «**почему модель так предсказала именно для этого объекта?**» и «**в какую сторону и насколько** повлияла каждая фича?»

> Именно проблема «непонятно, **как именно** фича влияет на предсказание» и была главной причиной появления SHAP.

## 7. Плюсы, минусы и ограничения

**Плюсы (из статьи):**

- ✅ **удобные** визуализация и интерпретация;
- ✅ **честный** расчёт важности фичей;
- ✅ можно оценить фичи для **конкретной подвыборки** — просто **отфильтровать датасет в** `pandas` и прогнать его через `shap` (пара строк кода);
- ✅ работает для **любых** моделей (деревья, линейные, нейросети);
- ✅ **аддитивность** — вклады точно складываются в предсказание.

**Минусы / на что обратить внимание:**

- ❌ **вычислительная сложность** — точный расчёт $O(2^n)$; нужны приближения (`KernelExplainer`);
- ❌ SHAP объясняет **поведение модели**, а **не причинно-следственные связи** реального мира (модель могла выучить ложную закономерность);
- ❌ при **сильно коррелированных** фичах вклады «делятся» между дублями — это перекликается с **мультиколлинеарностью** (`Проблема и решение мультиколлинеарности.md`);
- ❌ для больших датасетов `summary_plot` может быть **тяжёлым** по времени.

## 8. Чем SHAP полезен ML-инженеру

До этого мы говорили, **зачем** интерпретировать (бизнесу, врачу, клиенту). Но SHAP — это ещё и **рабочий инструмент самого инженера**: он ловит то, чего метрика не показывает.

> **Ключевая мысль:** метрика отвечает «**насколько** модель ошибается», SHAP — «**почему** и что чинить».

Ниже — **восемь** задач, в которых SHAP экономит недели отладки (плюс сводная таблица в §8.9).

### 8.1. Отладка: найти утечку и прокси-фичу

**Симптом:** в `summary_plot` (или в глобальных $\text{mean}(|\phi_i|)$) **одна фича объясняет почти всё** предсказание.

**Диагноз:** почти наверняка **утечка данных** или **прокси таргета**:

- `дата_закрытия_договора` (заполнена только у ушедших);
- `число_просрочек`, посчитанное **после** выдачи решения;
- target encoding по признаку, где в категории 1–2 объекта.

**Что делает инженер:** это ровно **шаг 3 «детектора утечки»** из `2.Кросс-валидация.md` (§7.6.8) — вместе с приёмом «удалил признак → метрика упала».

> Почему это выгодно: утечку видно **до** прода, за один вызов explainer'а, а не через месяц после релиза.

### 8.2. Анализ ошибок (error analysis)

1. Берём объекты, где модель **уверенно ошиблась**.
2. Смотрим **force plot** по каждому: какая фича «толкнула» не в ту сторону.
3. Если у 50 ошибок виновата **одна и та же** фича или их сочетание — это **систематическая** проблема.

Дальше выбор: фича-инжиниринг под этот срез, добор данных или выделение отдельной модели для сегмента. «Просто переобучим — рассосётся» тут не работает.

**Бонус:** SHAP можно считать не на всём датасете, а на **подвыборке** — например «только ошибочные предсказания по новым клиентам» (фильтруем датасет в `pandas`, пара строк кода).

### 8.3. Фича-инжиниринг и чистка признаков

- **Dependence plot** показывает **форму** зависимости. Видно порог или немонотонность → подсказка на новый признак: бинарный флаг «до/после», бакетизация, сплайн.
- Если $\text{mean}(|\phi_i|) \approx 0$ **на всех** объектах — признак не работает. Кандидат на удаление. Плюсы: быстрее инференс, меньше кода в проде, меньше поводов для утечки.
- Взамен «сырой» важности есть **направление**: можно проверить, что знак вклада совпадает со здравым смыслом домена (доход ↑ → риск ↓). Feature Importance такого не скажет.

### 8.4. Дубли и коррелированные признаки

- Два признака с **одинаковым** SHAP-паттерном (синхронно «толкают» одни и те же объекты) — скорее всего **дубли** → один можно убрать без потери качества.
- При сильной корреляции SHAP **делит** вклад между дублями: у обоих $\lvert\phi\rvert$ «средние», хотя по факту важен блок целиком. Это не баг, а следствие усреднения по коалициям — см. `Проблема и решение мультиколлинеарности.md`.
- **Приём из практики:** сгруппировать фичи по похожести их SHAP-векторов (кластеризация) — так находят избыточные блоки признаков и читают `summary_plot` осмысленными группами.

### 8.5. Взаимодействия признаков (interactions)

Кроме отдельных вкладов $\phi_i$ есть **SHAP interaction values** — парные: сколько из вклада фичи возникает **только в сочетании** с другой.

Это то, чего не покажет **ни** Feature Importance, **ни** коэффициент линейной модели: «фича важна, только когда другая фича в определённом диапазоне».

**Пример:** повышение зарплаты снижает отток **только** для сотрудников грейда X; для остальных грейдов вклад нулевой. Линейная модель такое не выразит, а interaction-значения покажут прямо.

### 8.6. Sanity check и приёмка модели перед продом

Чеклист «модель можно катить», который закрывается за полчаса:

- [ ] топ-признаки по $\text{mean}(|\phi_i|)$ **совпадают с ожиданиями домена**;
- [ ] **знаки** вкладов логичны (не «больше доход → больше риск»);
- [ ] нет фичи с **аномально большой долей** в общей важности (см. §8.1);
- [ ] для **эталонного объекта** объяснение совпадает с **ручным** расчётом (как с Bobby в §4);
- [ ] по **сегментам** (регион, канал, когорта) картина не противоречит здравому смыслу.

> Если объяснение противоречит домену — модель чиним или выкидываем **до** релиза. Метрика на тесте такое не поймает: модель может честно выучить **ложную** закономерность.

### 8.7. Объяснение решения: пользователю, бизнесу, регулятору

- **Локальное** объяснение (`force plot`) — то, что можно показать человеку: «кредит отклонён, потому что X и Y».
- **Требование «права на объяснение»:** GDPR (ст. 22) и 152-ФЗ — для автоматических решений нужен **объяснимый** вывод. SHAP — стандартный инструмент для этого.
- **Модель-агностичность:** один и тот же инструмент для бустинга, логита и нейронки → при смене модели объясняющий слой **не переписываем**.
- **Аддитивность** = объяснению можно верить: вклады **точно** складываются в предсказание, числа можно показать без «магии».

**Отдельный плюс — проверка на дискриминацию (fairness):** если таргет «протекает» через прокси-фичу (пол, возраст, индекс района), SHAP это **покажет явно**. Так нелегальную/неэтичную зависимость видно до того, как её найдёт юрист.

### 8.8. Мониторинг дрейфа в проде

SHAP считают не только на train:

1. Гоняем explainer на **новых батчах**.
2. Сравниваем **распределения** $\phi_i$ (и глобальные $\text{mean}(|\phi_i|)$) с обучающими.
3. Вклады «поехали» → либо изменились данные (**дрейф**), либо модель устарела → сигнал переобучить/проверить признаки.

**Почему это лучше «модель стала хуже»:** видно, **какая именно фича** сменила поведение — «фича №12 начала толкать в другую сторону», а не абстрактное падение метрики.

### 8.9. Сводная таблица: задача инженера → чем решать

| Задача инженера | Инструмент SHAP | На что смотреть |
|:---|:---|:---|
| Найти утечку / прокси-фичу | глобальный $\text{mean}(\lvert\phi\rvert)$, summary plot | одна фича объясняет почти всё |
| Разобрать ошибки | force plot по ошибочным объектам | какая фича «толкнула не туда» |
| Понять форму зависимости | dependence plot | порог, нелинейность, немонотонность |
| Выкинуть мусорные фичи | $\text{mean}(\lvert\phi\rvert) \approx 0$ | признак нигде не влияет |
| Найти дубли | похожие SHAP-паттерны у двух фичей | фичи ведут себя одинаково |
| Найти взаимодействия | SHAP interaction values | важность только в паре |
| Приёмка модели (§8.6) | глобальная картина + эталонный объект | согласуется ли с доменом |
| Объяснить решение (§8.7) | force plot одного объекта | понятное предложение для человека |
| Следить за дрейфом (§8.8) | SHAP на новом батче vs train | сдвинулись ли вклады |

### 8.10. Код: три инженерные задачи

```python
import numpy as np
import shap

explainer = shap.TreeExplainer(model)
sv = explainer.shap_values(X)          # матрица (объекты × фичи)

# 1) Глобальная важность = средний модуль SHAP по объектам
imp = np.abs(sv).mean(axis=0)

# 2) Детектор утечки: доля самой влиятельной фичи
#    больше половины всей важности -> идём проверять признаки
print("доля топ-фичи:", imp.max() / imp.sum())

# 3) Объяснение одного объекта (то, что показываем человеку)
shap.force_plot(explainer.expected_value, sv[0], X.iloc[0])
```

### 8.11. Чего SHAP **не** делает (границы применимости)

| Заблуждение | Как на самом деле |
|:---|:---|
| «SHAP объясняет **мир**» | объясняет **модель**. Если модель выучила ерунду — SHAP честно её «объяснит» |
| «SHAP заменяет валидацию» | утечка в признаках одинаково испортит и метрику, и SHAP. Нужны честный test и CV |
| «SHAP бесплатен» | `TreeExplainer` быстрый, `KernelExplainer` на большой модели — дорого. Считай на подвыборке |
| «$\lvert\phi\rvert$ = абсолютная важность» | при коррелированных фичах вклад **делится** между дублями (§8.4) |
| «SHAP = оправдание решения» | «объяснение ≠ оправдание»: если фича — прокси по полу, SHAP это **покажет** (полезно для fairness) |

### 8.12. Где SHAP в цикле ML

```text
данные → препроцессинг → обучение → метрика (CV)
                                       │
                                       ▼
                        SHAP: разбор ошибок, поиск утечек   ← §8.1–8.2
                                       │
                                       ▼
                       фича-инжиниринг / чистка признаков   ← §8.3–8.5
                                       │
                                       ▼
                            приёмка: sanity check           ← §8.6
                                       │
                                       ▼
                   прод → SHAP на новых батчах (дрейф)      ← §8.8
```

> **Итог:** для инженера SHAP — это **отладочный инструмент**, а не «картинка для презентации». Метрика говорит «насколько хорошо», SHAP — «почему так и что чинить».

## 9. Как это связано с другими конспектами

- В `5.Градиентный бустинг.md` (§8.3) SHAP упоминается как один из методов важности признаков наряду с **MDI** и **Permutation** — здесь разобран подробно. Помни правило выбора оттуда: **быстро — MDI, честно на отложенных данных — Permutation, вклад в каждое предсказание и при корреляциях — SHAP**.
- Проблема «важность показывает *насколько*, но не говорит *как*» перекликается с трактовкой **весов** в `1.Линейные модели.md` и `Важность в контексте весов.md`.
- Если описывать сам принцип усреднения вклада — это близко к идее **теории игр**, а «размазывание» вклада между дублями напрямую связано с **мультиколлинеарностью**.
- В `2.Кросс-валидация.md` (§7.6.8, «детектор утечки») один из шагов — «посмотри важности признаков, а лучше **SHAP**»: одна доминирующая фича = сигнал утечки. Обратная сторона (как это ловить со стороны SHAP) — §8.1 здесь.

## 10. Шпаргалка для запоминания

| Вопрос | Ответ |
|:---|:---|
| Что расшифровывается SHAP? | **SH**apley **A**dditive ex**P**lanations |
| Откуда пришли значения Шэпли? | из **теории игр** (дележ призового фонда по вкладу) |
| Что такое «игроки» и «призовой фонд»? | фичи = игроки, предсказание = фонд |
| Формула значения Шэпли? | $\phi_i = \sum_{S \subseteq N\setminus{i}} \frac{\lvert S\rvert!\,(n-\lvert S\rvert-1)!}{n!}\big(p(S\cup{i})-p(S)\big)$ |
| Свойство аддитивности? | $f(x) = \phi_0 + \sum_i \phi_i$ |
| Что такое $\phi_0$? | базовое значение $p(\varnothing)$ (все фичи неизвестны) |
| Главное отличие от Feature Importance? | SHAP показывает **КАК** (направление + величину) и **для каждого объекта**, а не только «насколько» в среднем |
| Инструмент для деревьев? | `TreeExplainer` (XGBoost / LightGBM / CatBoost / sklearn) |
| Универсальный (для любой модели)? | `KernelExplainer` (медленный) |
| Числа-пример из статьи (Bobby, фича `age`)? | $0.9875 + 0.5125 = 1.5$ |
| Как читать summary plot? | слева класс $0$, справа класс $1$; толще — больше точек; краснее — выше значение фичи |
| Зачем SHAP **инженеру**? | отладка: утечка/прокси, разбор ошибок, чистка фичей, приёмка, дрейф |
| Быстрый детектор утечки через SHAP? | доля топ-фичи в сумме $\text{mean}(\lvert\phi\rvert)$ больше $0.5$ → идём проверять признаки |
| Что показывает SHAP interaction? | вклад фичи, возникающий **только в паре** с другой |
